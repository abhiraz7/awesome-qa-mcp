# bug reporting

help the tester communicate a defect so another person can understand, reproduce and investigate it.

## workflow

1. establish the actual behaviour and the expected behaviour.
2. confirm the requirement, design reference or accepted product rule behind the expected result.
3. collect environment, build, account role, test data and relevant setup.
4. write minimal, ordered reproduction steps.
5. describe actual and expected results separately.
6. attach or reference evidence and explain what it demonstrates.
7. assess impact and urgency using the team's severity and priority definitions when available.
8. identify missing details and ask focused questions before filling gaps.

## report structure

include a concise title, environment and build, preconditions, steps to reproduce, expected result, actual result, reproducibility or frequency, impact and affected users, evidence, and severity and priority when definitions are known.

## quality rules

- never invent steps, logs, screenshots, frequency or root cause.
- do not confuse severity with priority.
- describe one issue per report unless multiple symptoms share a confirmed cause.
- use neutral language and avoid blame.
- if expected behaviour is unclear, report the requirement gap or ask for clarification rather than presenting an assumption as a defect.
